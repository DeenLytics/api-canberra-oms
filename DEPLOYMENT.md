# Deployment

Pushing to `main` builds on GitHub Actions and rsyncs the result to the VPS.
Composer runs on the runner, never on the cPanel box.

There is no frontend build step. `package.json` carries only vite and tailwind
as devDependencies, there is no lockfile, and production has never had
`node_modules` or `public/build` — verified on the server. This is an API; the
only `@vite` reference is in Laravel's default `welcome.blade.php`. `rsync`
excludes `public/build` anyway, so adding a build later will not be undone by
`--delete`.

Workflow: [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml)

| | |
|---|---|
| Server path | `/home/canberra-api/public_html` |
| Server | `62.72.47.10` |
| Web server | Apache 2 + PHP-FPM, per-user pools |
| Web PHP | 8.2, via the FPM pool at `/etc/php/8.2/fpm/pool.d/` |
| CLI PHP | 8.3.32 — what `php artisan` runs as |
| File owner | `canberra-api` — the FPM pool user |
| Trigger | push to `main`, or **Run workflow** in the Actions tab |

## Required repository secrets

| Secret | What it is |
|---|---|
| `SSH_HOST` | VPS hostname or IP |
| `SSH_USER` | cPanel/SSH user that owns the path above |
| `SSH_PORT` | SSH port — omit if 22 |
| `SSH_PRIVATE_KEY` | Private half of the deploy key, whole file |
| `SSH_KNOWN_HOSTS` | Output of `ssh-keyscan -H <host>` |

No application secrets are needed here. The server's own `.env` stays on the
server and is never overwritten — see the excludes below.

Run `./setup-secrets.sh` from the parent working folder to set the SSH secrets
for all three repos at once.

CI installs vendor against PHP 8.2 deliberately: that is what serves web
requests, and it is the stricter of the two versions on the box. `composer.json`
declares `"php": "^8.2"`, so the resulting `platform_check.php` is satisfied by
both the 8.2 web runtime and the 8.3 CLI.

## What is deliberately NOT deployed

The rsync excludes in this workflow are the safety-critical part of the file.
Read them before changing anything:

| Excluded | Why |
|---|---|
| `.env` | Server-owned. Holds DB and mail credentials. |
| `storage/` | **`storage/app/public/products` holds 210 uploaded product images. This is user data and exists nowhere else — not in Git, not in the build artifact. `--delete` without this exclude would erase every product photo.** |
| `public/storage` | The `php artisan storage:link` symlink into `storage/`. |
| `bootstrap/cache/` | Regenerated by the workflow. |
| `.htaccess` | The server's copy stays authoritative. |

> The images have no backup other than the server filesystem. That is a
> standing risk independent of deployment and worth fixing separately.

## Ownership

PHP-FPM serves this site from a per-user pool running as `canberra-api`, so
every file has to be readable by that user. `rsync -a` as root would stamp the
GitHub runner's uid onto the tree instead — on this host that uid maps to an
unrelated account, and it is precisely what took the API down on its first
automated deploy. The workflow passes `--no-owner --no-group` and chowns the
tree afterwards.

## bootstrap/cache must be deleted, not just cleared

`bootstrap/cache` is excluded from rsync so the runner's copy never ships. The
server's copy has to be **deleted**, not regenerated.

CI builds vendor with `--no-dev`. A `packages.php` written back when composer
ran *with* dev dependencies still registers `Laravel\Pail`'s service provider,
which is no longer on disk. The app then cannot boot at all — which means
`php artisan optimize:clear` cannot run either, because it needs a bootable
app. Removing the files outright is the only thing that recovers it.

This is what caused the first deploy's 500, alongside the ownership problem.

## A note on the `.htaccess`

The file carries a `# php -- BEGIN cPanel-generated handler` block. **There is
no cPanel on this server** — `/usr/local/cpanel` does not exist. The block is
inherited from wherever this app was hosted before, and the handler it names
(`application/x-httpd-ea-php82___lsphp`) does not exist here either. It is
inert: the vhost's own `SetHandler` for PHP-FPM takes precedence.

It is left in place because it does no harm, but do not read it as evidence of
how this box is configured. It misled exactly that way once already.

## Migrations

Migrations do **not** run on push. They run only from a manual dispatch with
the `run_migrations` box ticked:

Actions → **Deploy API** → **Run workflow** → tick *Run php artisan migrate*.

This keeps a routine code deploy from altering the schema by accident.

## Caches

After every deploy the workflow runs `optimize:clear` before rebuilding the
config, route and view caches. Clearing first is deliberate — a stale config
cache survives a deploy and silently serves the old values.

## Smoke test

The final step calls `GET /api/v1/site-setting` and fails the run on anything
other than 200. That endpoint is unauthenticated and is what the admin and SR
apps use for their suspend check, so it exercises routing, config and the
database in one request.

## First run — do this manually

1. Back up the server directory:
   ```bash
   ssh <user>@<host> "cp -a /home/canberra-api/public_html /home/canberra-api/public_html.bak-$(date +%F)"
   ```
2. Actions tab → **Deploy API** → **Run workflow**, migrations unticked.
3. Watch the smoke test.
